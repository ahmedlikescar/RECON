RECON
INTELLIGENT BINARY ANALYSIS & FUNCTION SIMILARITY ENGINE
Complete Engineering Master Prompt • Software Requirements Specification • Use Cases • ML Research Plan
Version 1.0  |  October 2026  |  Local-first, open-source, no paid AI APIs
Executive summary
RECON is a static binary analysis application that ingests authorized PE/ELF binaries, discovers and disassembles functions, extracts instruction and control-flow features, and ranks potentially equivalent functions across different compilations using reproducible machine-learning embeddings. The product exposes evidence, uncertainty, and provenance instead of claiming to recover source code or prove maliciousness. It must never execute analyzed binaries.

1. Product scope and goals
Primary problem: compare functions from separately compiled versions of open-source programs and retrieve semantically related implementations despite changed instruction sequences.
Target users: students, reverse engineers, compiler researchers, and security analysts working on binaries they are authorized to inspect.
Core workflows: import binary → static parse → discover functions → disassemble → extract CFG/features → compare → inspect evidence → export findings.
MVP scope: x86-64 ELF, static analysis, instruction baseline, labeled cross-optimization retrieval evaluation, local desktop-served web UI.
Later scope: PE x86-64, neural embeddings, scalable FAISS index, CFG graph encoder, multi-binary collections, and offline research reports.
Out of scope: dynamic malware execution, exploitation, automated patching, decompilation accuracy guarantees, definitive malware verdicts, and bypassing software protections.

8. System workflows
Import: browser → FastAPI validation → SHA-256 and format metadata → SQLite record → persistent job → sandboxed parser → function discovery → disassembly/CFG → stored artifacts → UI.
Similarity: select query function → check feature schema/model version → normalize features → compute embedding → FAISS/exact nearest neighbors → metadata filters → ranked candidates → side-by-side evidence.
Training: collect authorized source → compile build matrix → match function lineages → extract features → project-grouped split → baseline → model training → checkpoint → validation → frozen test evaluation.
Failure: worker records phase-specific failure and diagnostic → deletes incomplete temporary artifacts → leaves previous valid indexes intact → user can retry when safe.
Deletion: identify owned binary → remove references and derived artifacts → update index atomically → verify deletion and return status.

11. ML methodology and scientific validity
Dataset: choose a small set of permissively licensed C/C++ projects; compile same source revisions with GCC and Clang and optimization levels O0/O1/O2/O3 where feasible; retain complete build manifests.
Ground truth: link corresponding functions using source-level identifiers/debug symbols/build metadata; record ambiguous/inlined/removed functions rather than forcing incorrect labels.
Leakage control: group by source function lineage and ideally by project across splits. Avoid using near-identical source functions in both train and test.
Baseline A: normalized opcode histogram with cosine similarity. Baseline B: instruction n-gram TF-IDF. Baseline C: CFG statistics.
Model v1: token embedding + masked mean pooling or small 1D encoder; contrastive/triplet training on positive and hard-negative function pairs.
Model v2: graph encoder using basic-block features and CFG adjacency only if v1 is validated.
Evaluation: Recall@1/5/10, MRR, median rank, latency, index memory, subgroup performance by compiler/optimization/function length, and qualitative false-positive analysis.
Reproducibility: dataset/model cards, code commit, seeds, environment, hardware, epoch count, optimizer, hyperparameters, checkpoint hashes.
Threat to validity: inlining, dead-code elimination, compiler-generated helpers, missing symbols, disassembly errors, and datasets with trivial compiler signatures.
12. Security, ethics, and scope restrictions
Only analyze binaries the operator is authorized to inspect. Respect licensing and intellectual property rights.
Never execute uploaded binaries. Static parsers are still attack surfaces; run in isolated worker processes with memory/time limits, restricted filesystem access, and no network access where feasible.
Do not automatically classify a file as malware based on similarity alone. Report evidence and uncertainty.
Do not use analysis to facilitate exploitation, bypass access controls, or distribute malicious payloads.
Public hosting is not required; default to local-first deployment. If exposed publicly, add identity, quotas, secure file storage, per-user isolation, and abuse monitoring.
Validate every file path, identifier, index metadata version, and exported filename. Avoid unsafe pickle loading of untrusted model artifacts.

20. Reverse Engineer Anything (REA) integration — mandatory extension
This section extends, and does not replace, Sections 0–19. All original requirements, use cases, ML methodology, security constraints, and acceptance criteria remain applicable. REA is an optional analysis adapter and agent-investigation aid; RECON remains an independent binary function similarity ML product.
20.1 Verified upstream and scope
Official upstream: https://github.com/morluto/rea ; documentation: https://rea.tools ; npm package: rea-agents. Verify current upstream release, license, and provider compatibility before implementation. Do not install from lookalike repositories or assume forks are official.
REA provides MCP/CLI-driven investigation and evidence for supported binary and application formats. Native disassembly/decompilation relies on a configured provider such as Ghidra, Hopper, or IDA; REA does not itself supply commercial tool licenses.
Default to free Ghidra for native analysis. Capstone/LIEF remain available for lightweight parsing and fallback. Keep the RECON embedding model, dataset builder, FAISS retrieval, and evaluation suite independently implemented.
REA may be used by the coding agent during RECON development and exposed as an opt-in, local analysis provider at runtime. The latter requires an explicit adapter, capability discovery, evidence normalization, and user approval for potentially stateful operations.
20.2 Architecture and integration contract
Define AnalysisProvider interface: capabilities(), healthcheck(), inspect_binary(), list_functions(), inspect_function(), get_call_references(), get_evidence(). Keep structured typed outputs and provenance.
Implement NativeGhidraProvider and REAProvider adapters; route through AnalysisOrchestrator with configurable provider priority, timeout, cancellation, and fallback. REA failure must never block core RECON analysis.
REAProvider must use the supported MCP or CLI interface documented by the pinned REA version; never invent tool names, output schemas, or capabilities. Run setup only with user approval; record versions and configuration in docs/REA_INTEGRATION.md.
Normalize provider output into RECON FunctionEvidence: binary_id, function_id, provider, provider_version, instruction_range, assembly, pseudocode (optional), symbols, references, source_artifact_hash, evidence_links, limitations, collected_at.
Keep REA-derived pseudocode and observations distinct from ML predictions. Display similarity scores as similarity metrics, not certainty or proof of behavior. Never treat an agent explanation as ground truth.
REA-assisted AI narrative explanations are optional and disabled by default. The standard RECON analysis path must run without paid API keys or an external model provider.
Only process binaries users own or are authorized to analyze. Default to static inspection. No execution of untrusted uploads, bypass of access controls, DRM, anti-cheat, or licensing checks.
20.3 Additional functional requirements
FR-041 — REA provider registration: RECON shall expose REA as an optional provider with explicit enable/disable configuration.
FR-042 — Capability discovery: RECON shall report installed REA version, configured native provider, and available inspection capabilities.
FR-043 — REA function evidence: For supported targets, RECON shall request and persist evidence-backed function inspection results through the REA adapter.
FR-044 — Provider fallback: When REA is absent or fails, RECON shall continue core static analysis using the existing pipeline.
FR-045 — Evidence provenance: Every REA-derived field shall retain tool identity, version, source address/range, and evidence limitations when available.
FR-046 — Assisted investigation: Users may request an opt-in, evidence-based explanation of a selected function; the interface shall disclose any configured external AI provider.
FR-047 — Function matching independence: ML embedding training and similarity retrieval shall work without REA and shall not depend on generated prose.
FR-048 — Consent and controls: Users shall approve provider installation/configuration and any operation that executes or modifies a target.
FR-049 — REA report export: Reports shall distinguish disassembly facts, REA evidence, model similarity outputs, and human/agent hypotheses.
FR-050 — Integration diagnostics: Users shall see actionable errors for missing Node.js, missing REA, incompatible version, missing Ghidra, and provider timeouts.
20.4 Additional non-functional requirements

21. Final product and machine learning implementation directive
RECON is a local-first static binary analysis and machine-learning function-similarity application. Its primary demonstration is matching source-corresponding functions between differently compiled builds or software versions. The coding agent must deliver working, measured training and inference rather than mocked predictions. REA is an optional evidence provider, not the ML engine.
21.1 Mandatory end-to-end ML workflow
1. Acquire source: Select permissively licensed C/C++ projects; pin revisions, license metadata and provenance. Include multiple independent projects and test programs.
2. Compile reproducibly: Build source using pinned GCC and Clang versions, x86-64 initially, optimization O0/O1/O2/O3 where supported; retain build logs, symbols and source mapping only for ground truth.
3. Extract functions: Use Ghidra/Capstone/LIEF and a stable extraction schema. Record function boundaries, instruction tokens, CFG features, compiler settings and extraction confidence.
4. Build pairs and splits: Match binary functions to verified source identities; reject ambiguous mappings, inlined or merged functions where uncertain. Split by source project before pair generation to avoid leakage.
5. Train baselines: Implement token n-gram TF-IDF, normalized opcode histogram and structural-feature similarity as reproducible baselines.
6. Train encoder: Implement compact shared-weight Siamese encoder in PyTorch; use normalized embeddings, contrastive/InfoNCE loss, documented negatives, validation-based checkpoints and early stopping.
7. Evaluate: Benchmark held-out projects and cross-compiler/optimization subsets; measure Recall@1, Recall@5, MRR, precision of accepted matches, false matches, latency and memory.
8. Package and serve: Save model weights, vocabulary, normalization spec, architecture config, provenance and version; load once for inference and index candidate functions in FAISS.
9. Integrate: Expose asynchronous comparisons in FastAPI, persist ranked matches, show evidence in React, and permit REA-assisted investigation without affecting the matching scores.
10. Reproduce: Provide one-command demo and separate reproducible train/evaluate commands, artifact hashes and honest hardware/runtime records.
21.2 Training and evaluation safeguards
Never train on or select hyperparameters using the final held-out test projects. Deduplicate near-identical source code across splits.
Treat compiler optimizations, inlining, link-time optimization, stripped symbols, architecture differences and function-boundary errors as explicit threats to validity.
Only report real measured results with dataset size, class balance, compiler versions, seed, hardware and run duration. Never invent accuracy, benchmarks, or a trained checkpoint.
Similarity is a ranking signal, not a calibrated probability or proof of semantic equivalence. Provide unknown/no-match behavior.
Train on CPU by default with small dataset/model presets; GPU is optional and never mandatory for core operation.
If training cannot run in the execution environment, deliver verified scripts and baselines, mark neural weights as unavailable, and keep the application functional.
